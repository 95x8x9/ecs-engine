# ECS View 최적화 측정 결과

이 문서는 GitHub 이슈 #24에서 진행한 ECS View 및 sparse-set 접근
최적화의 단계별 성능 변화를 기록한다. 모든 시간은 한 번의 시뮬레이션
업데이트에 걸린 `ms/step`이며, 낮을수록 좋다.

측정일: 2026-09-22

| 단계 | 커밋 | 변경 내용 |
|---|---|---|
| Baseline | `96c875e` | View 접근 최적화 전 |
| Driver 검사 생략 | `d24f2f4` | `ContainsAll()`에서 첫 번째 저장소의 존재 여부 재검사 생략 |

## View 수명과 구조 변경 제약

`View`는 생성 시점에 각 `ComponentStorage`의 포인터를 저장하며 엔티티 목록을
복사하지 않는다. 따라서 같은 View의 `Each()`를 다시 호출하면 해당 저장소의
현재 엔티티를 순회하지만, 다음 제약을 지켜야 한다.

- View를 생성할 때 필요한 컴포넌트 저장소가 없었다면 해당 포인터는
  `nullptr`로 유지된다. 이후 Registry에 그 컴포넌트 저장소가 생성되어도 기존
  View에는 반영되지 않으므로 View를 다시 생성해야 한다.
- `Registry::Clear()`는 컴포넌트 저장소를 제거하므로 기존 View가 보관한 모든
  저장소 포인터를 무효화한다. Registry가 파괴된 뒤에도 View를 사용할 수 없다.
- `Each()` 콜백 안에서 Entity를 생성·삭제하거나 컴포넌트를 추가·삭제하는 구조
  변경은 금지한다. 특히 driver storage가 변경되면 순회 중인 dense 엔티티 배열의
  재할당이나 swap-remove로 현재 인덱스와 참조가 무효화될 수 있다.
- 기존 컴포넌트의 값만 변경하는 것은 허용된다. 구조 변경이 `Each()` 호출 사이에
  일어났고 저장소 자체가 유지됐다면 다음 호출은 갱신된 dense 배열을 사용한다.

일반 View를 사용하는 현재 시스템은 `Each()` 콜백 안에서 대상 저장소의 구조를
변경하지 않는다. 반복 순회용 CachedView의 더 긴 수명과 무효화 규칙은 다음 절에
별도로 기록한다.

## CachedView dense index 캐시

반복 이웃 순회에서 남아 있던 pair당 `Velocity` sparse 조회를 제거하기 위해
`CachedView<Transform, Velocity>`를 추가했다. 일반 `View`가 저장소 포인터만
보관하는 것과 달리 CachedView는 매칭 Entity와 각 저장소의 dense index를 한 번
수집한다. 이후 `Each()`는 저장된 index로 dense component 배열에 직접 접근한다.

BoidSystem은 이웃 CachedView를 프레임 간 재사용한다. 컴포넌트 값 변경은 현재
dense index로 최신 값을 읽으므로 허용한다. 컴포넌트 추가·삭제, Entity 파괴,
Registry 초기화는 저장소별 structural revision과 Registry storage epoch으로
감지하며, 다음 업데이트 시작 시 캐시를 다시 구축한다.

수정 전 `d88ef71`과 CachedView 작업 트리를 별도 Release 실행 파일로 빌드하고
번갈아 8회씩 실행했다. 실행 순서는 매 반복마다 뒤집었으며 logical CPU affinity
`0x2`, `AboveNormal` 우선순위를 적용했다. seed와 timestep, agent별 warmup 및
측정 step은 위의 기존 조건과 같다. 캐시는 첫 warmup update에서 구축되므로 아래
수치는 장기 실행의 steady-state 비용을 비교한다.

| Agents | 조건 | Mean ms/step | Median ms/step | Min ms/step |
|---:|---|---:|---:|---:|
| 100 | 기존 View | 0.082396 | 0.081869 | 0.078820 |
| 100 | CachedView | 0.062134 | 0.061863 | 0.058571 |
| 500 | 기존 View | 1.386959 | 1.388124 | 1.322567 |
| 500 | CachedView | 0.909590 | 0.889965 | 0.868300 |
| 1,000 | 기존 View | 5.485404 | 5.484657 | 5.364691 |
| 1,000 | CachedView | 3.720594 | 3.713090 | 3.600842 |

| Agents | 평균 개선율 | 중앙값 개선율 | 최솟값 개선율 |
|---:|---:|---:|---:|
| 100 | 24.59% | **24.44%** | 25.69% |
| 500 | 34.42% | **35.89%** | 34.35% |
| 1,000 | 32.17% | **32.30%** | 32.88% |

모든 agent 수에서 평균, 중앙값, 최솟값이 함께 개선됐다. 따라서 결과는 기존
View 생성 비용이 아니라 naive all-pairs 내부 루프의 sparse-to-dense 조회가 실제
병목 중 하나였다는 가설과 일치한다. 알고리즘 복잡도는 여전히 `O(N²)`이므로 다음
주요 최적화 단계는 예정된 3D Grid 공간 분할이다.

## 채택하지 않은 후보: MovementSystem 순회 결합

직전 단계인 `09aff4e`의 3회 순회와 `Transform + Velocity + Acceleration +
BoidParameters` View 하나로 결합한 작업 트리를 8회 교차 측정했다. 결합된
콜백은 기존과 동일하게 가속도 반영, 속도 제한, 위치 이동 순서로 실행한다.

| Agents | 조건 | Mean ± SD | Median | Min | 평균 변화 | 중앙값 변화 | Best 변화 |
|---:|---|---:|---:|---:|---:|---:|---:|
| 100 | 3회 순회 | 0.043901 ± 0.002252 | 0.042813 | 0.041797 | - | - | - |
| 100 | 1회 결합 순회 | 0.044133 ± 0.001860 | 0.043381 | 0.042638 | 0.53% 저하 | 1.33% 저하 | 2.01% 저하 |
| 500 | 3회 순회 | 0.726272 ± 0.020739 | 0.719197 | 0.711804 | - | - | - |
| 500 | 1회 결합 순회 | 0.729892 ± 0.016611 | 0.723518 | 0.716491 | 0.50% 저하 | 0.60% 저하 | 0.66% 저하 |
| 1,000 | 3회 순회 | 4.007400 ± 1.969277 | 2.990462 | 2.912297 | - | - | - |
| 1,000 | 1회 결합 순회 | 4.687997 ± 2.399995 | 3.200900 | 2.941419 | 16.98% 저하 | 7.04% 저하 | 1.00% 저하 |

100개와 500개에서는 평균, 중앙값, 최솟값이 모두 소폭 악화됐다. 1,000개
평균과 중앙값은 느린 이상치의 영향을 크게 받았지만, 간섭이 가장 적은 최솟값도
1회 결합 순회가 약 1% 느렸다. 기존 세 View와 결합 View는 완전한 Boid 하나당
총 세 번의 sparse 포함 검사를 수행한다는 점이 같아서, 결합으로 줄어드는 것은
주로 반복문과 콜백 호출 비용이다. 반면 기존 루프는 각각 두 컴포넌트 저장소만
연속 접근하고 결합 루프는 네 저장소를 함께 접근한다. 전체 시간은 `O(N²)` 이웃
검색이 지배하므로 순회 결합의 이득은 작고, 이번 측정에서는 일관된 개선이
확인되지 않았다. 성능을 기준으로는 3회 순회 구현을 유지하는 편이 낫다.

## 기능 검증

- Visual Studio 2022 Debug 전체 빌드 통과
- Registry/View 동작과 OOP/ECS 동등성 테스트를 포함한 78개 테스트 통과
- 없는 컴포넌트와 오래된 Entity handle은 `FindComponent()`에서 `nullptr`로 처리

  정렬을 가정하지 않음
